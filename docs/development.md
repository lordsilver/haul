# Development

The engine is `crates/haul-core`, the server and its API `crates/haul-web`, and the desktop app `crates/haul-desktop`. Plain `cargo build` and `cargo test` cover the engine and the server; add `--workspace` for the desktop app, which needs WebKitGTK on Linux (see [Installing](install.md)).

## The web UI

The web UI lives in `crates/haul-web/ui` (React, TypeScript, Tailwind and shadcn/ui, built with Vite). Git keeps the built page in `ui/dist`, so building Haul needs no Node.

To change it, with Node 26 and pnpm (`mise install` sets them up): `pnpm install`, then `pnpm dev` for a live page that talks to a Haul already running on port 8765, and `pnpm check && pnpm test && pnpm build` before committing the sources together with `dist`. CI fails when `dist` does not match the sources.

Buttons say their rank by their look, the same everywhere: **primary** (filled, the default variant) for the one thing to do next in a place, at most one per toolbar, card or dialog; **secondary** (`outline`) for a useful alternative that applies now; **tertiary** (`ghost`) for utilities and for what does not apply right now, shown disabled. The rank follows the state: **Start** is primary while files wait, **Resume all** while everything is paused, **Pause all** never is.

`pnpm test` runs the page's own tests ([Vitest](https://vitest.dev)), each `*.test.ts` beside the module it tests. They cover what the page decides for itself: picking rows, the list's entries and search, the captions, the messages it words and reading `#/add/` links. What a row is and what it may do comes from the engine, and its tests are in Rust.

`cargo test` regenerates the page's types from the Rust ones (`ui/src/lib/bindings`).

## The walk suite

`crates/haul-desktop/src/walk_suite.rs` walks made-up pages in a real browser, as the desktop app walks a page on a site Haul has no code for: one scenario per kind of obstacle (an ad's layer over the button, a pop-under, a cookie dialog that traps clicks, countdowns, a step that opens in a new tab, a script that loads late, an ad that moves the tab, a script's dialog that freezes the page, a captcha that stalls, a mirror index, a file's page, a stand-in for the CutCaptcha widget with a generated jigsaw, a check page that starts over when a script in its world looks up its captcha's field). It is part of `cargo test` and runs where Edge or Chrome is found (Windows, or `HAUL_CHROMIUM`), four scenarios at a time, in about a minute; elsewhere it is skipped. `HAUL_WALK_ONLY=<words>` keeps to the scenarios whose name holds them. A scenario that fails is printed with its pass's signals (what was pressed, what the widget's turn did, how the pass ended), as debug mode would stream them.

It is also the benchmark of how fast Haul gets past what sites put in the way. Its scorecard (printed with `--nocapture`) tells, for each scenario, the time its pages force by themselves (`floor`: their countdowns), what the walk took beyond that and beyond what the machine's browser takes to start and stop (measured first, so a slow CI machine and a fast desktop tell the same story), and the scenario's limit; the total of the walks' own time is the number to bring down. A change that makes a walk faster lowers it, one that slows a scenario past its limit fails the suite. Lower a scenario's limit when a strategy makes it reliably faster, so the gain is kept.

When a real page defeats the walk, add its obstacle as a scenario first, made up: the pages are served from the test itself on `<name>.localhost`, and a walk ends at an address on a host Haul knows, which is never loaded. A scenario marked `gap` is a known failure: it is run and told, and fails the suite once it passes, so the mark comes off with the fix.

How real sites fare is not in the repository: the `haul-windows-test` skill's `scorecard.py` gives a private list of links to a test copy and compares the run with the one before.

## Dependencies

CI checks the dependencies on Linux: `cargo deny check advisories bans sources` (settings in `deny.toml`) fails on a crate with a known vulnerability, a yanked one, or one from anywhere but crates.io, and `pnpm audit --prod` on a known vulnerability in what the page ships. Run the first in the repository root and the second in `crates/haul-web/ui` to check before pushing; a failure is usually fixed with `cargo update -p <crate>` or `pnpm update <package>`.

## Workflow actions

The workflows reference actions by major version tag, and `.github/workflows/actions.lock` records the exact commit GitHub runs for each, with the ID of the repository it must come from ([workflow dependency lockfiles](https://docs.github.com/actions/concepts/security/workflow-dependency-lockfiles), a public preview). The lockfile is generated by the [`gh actions-lock`](https://github.com/github/gh-actions-lock) extension at the version CI pins in `ci.yml`; never edit it by hand. After adding or changing a `uses:` line, run `gh actions-lock --no-narrow`, so major tags stay as written, and commit the workflow and the lockfile together. `gh actions-lock --relock` moves to newer releases within each major version; review its diff like a version bump, since a move back to an older commit is not flagged. CI runs `gh actions-lock --verify`.

CI's checks run on every push to `main` and on every pull request, except in a stack of pull requests (`gh stack`): there only the top pull request runs them, since its branch holds every layer below it.
