# Containers and wrappers

A container is a file that holds links: a `.dlc` from JDownloader, or plain text with links in it. Dropping one on the window, opening it, passing it on the command line or importing it through the [HTTP API](api.md) shows the links in the Add dialog — nothing downloads until **Add** — or adds them at once with **Settings › Add dropped links and files right away**. From there each link behaves as if it had been pasted; what that means is in [How downloads behave](downloading.md).

## Text files

Any file whose name does not end in `.dlc` is read as text, so `.txt` is the common case but neither the name nor any format matters: every `http(s)` link in the file is taken, one per line or not, with trailing punctuation trimmed.

## `.dlc` files

A `.dlc` holds an encrypted list of links, and decrypting it needs JDownloader's key service once: the file's last 88 characters go to the service, its answer decrypts the file key, and that key decrypts the list. Import therefore works while the service is reachable, and the names and the package (the subfolder its links get) come out of the decrypted list; a name the list marks unknown (`n.A.`) counts as none, so that link is named the way a pasted one is. The service goes through the proxy like a host, even for a `.dlc` fetched from a host you let go direct.

## Wrapper pages

A wrapper page holds a release's files behind a gate, on many hosts or on one (a release may come as one wrapper per host); filecrypt.cc and fileguard.cc are the common ones. Haul unwraps a wrapper link as soon as you add it, whatever else the queue is doing, and keeps it in the **Wrappers** section: what it found, or why it did not open. Its files join the list **not started**, each once: the same file from another host, on this wrapper or another one, becomes a mirror of it, matched by file name (a host that hides the name joins once Haul has learned it). Nothing downloads until you start it — one file, an archive's parts together, or **Start all** on the wrapper. **Remove** on the wrapper takes the files that never started with it.

A fileguard.cc link needs no person: its gate is a proof of work, and Haul solves it. Every link of a vault (`fileguard.cc/<vault>/<host>`) shows the same page, so the vault is added and solved once whichever of its links you add. The page lists each host's links in the same order, so a release in parts becomes one row per part with every host as a mirror, named after the hosts whose links name it; the host you prefer downloads it and the others are failovers. Solves run one at a time, a vault Haul has solved before is read without a new solve, and a solve fileguard.cc refuses (a burst of them can be) is tried again later.

A filecrypt.cc container needs no person either. Its gate is a checkbox, "I am a human", that asks for a proof of work and a report of the click: Haul works the proof and sends what a click on the box reports, under its own user agent and with nothing about canvas, graphics, audio, fonts or screen, which it does not have. The solved page holds the container's links as Click'n'Load data with their key beside them, so Haul decrypts them itself, with no key service; the page's `.dlc` is the fallback. The page's table names each link's file, in the same order, so links whose address carries no name (1fichier, gofile, vikingfile) still join the same file from other hosts and other containers: six containers of one release on six hosts become one row per part with six mirrors. Solves run one at a time, since filecrypt.cc asks more work of an address that solves in bursts, and a container Haul has opened before is read without a new solve. A container behind a password, or a solve filecrypt.cc turns away, waits for you in **Wrappers**: solve the gate in the app's browser (it goes through the proxy like the downloads) and the page offers the container as a `.dlc` download; hand the link back, or paste it, and Haul fetches and unpacks it like any dropped container. A `.dlc` link added on its own is a wrapper too. If the link handed back fails, the page waits for you again.

A mirrored.to link is one file uploaded to many hosts: Haul reads its page, the hosts' table behind it and each host's link (no person needed), and the file becomes one row with every host that took it as a mirror.

A web page that only lists links, such as a release's post on a blog or forum, becomes a wrapper of them: add its address and Haul reads the page for its links to hosts it knows and to wrappers (filecrypt.cc, fileguard.cc, mirrored.to), in the page's order, leaving the site's own links and ads out. The page gets a card under **Wrappers**, and its files join the list not started, as any wrapper's do. A page you add that links no host Haul knows waits for you under **Needs you**: it is likely a host's own page with a captcha or a button. One that clipboard watching brought in is left alone without a word.

Either way, a link the queue already holds is not added again: a file the queue already has keeps its own row, state and turn, and the wrapper's links join it as mirrors.
