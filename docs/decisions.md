# Decisions

Design decisions and why they were made. What the behaviour is, in full, is in [How downloads behave](downloading.md), [Using Haul](usage.md) and [Configuration](configuration.md). Newest last.

## Rust rewrite of a Python prototype

The first version was a Python (aiohttp) script with a web UI. Its logic (mirror grouping, probing names before downloading, per-host slots and cooldowns, the shared speed limit, proxy routing with explicit direct approval, the browser hand-off for interactive host pages) was tested and kept; Haul ports it to Rust. The prototype kept its queue next to the script, so a second copy loaded and rewrote the user's real queue; Haul's state lives in a per-user data folder, an exclusive lock refuses a second instance on the same folder, and saves go through a temporary file and a rename.

## Tauri 2, not the Tauri 3 alpha, and not Electron

When the project started (October 2026), Tauri 3 was at `3.0.0-alpha.4`; there was no beta. Its changes so far are plugin and Linux runtime refactors that this app does not need, while its plugins and documentation were alpha too. Tauri 2.12 is current and stable; the shell is small enough that moving to 3 when it ships is a short change.

On Windows, Tauri renders with WebView2, which is the same Chromium engine Electron bundles, so the page performs the same; Tauri leaves out the bundled Chromium and Node.js, which makes for a small installer, and its webview reports downloads, which the in-app browser needs. Reports of Electron outperforming Tauri mostly come from Linux, where Tauri uses WebKitGTK, or from apps that push a lot of data through Tauri's IPC; Haul's UI does not use the IPC at all.

## One UI, served by the engine

The web UI is a page served by the engine's local HTTP server, and the desktop window simply loads that page. The same UI then works headless in any browser (or from another machine's browser through an SSH tunnel), the browser-facing API is the one the UI uses, and the desktop shell stays a few hundred lines. The shell adds only what a page cannot do itself: the tray, notifications, single-instance handling, file associations and the in-app browser, the latter reached through one API route.

The page is React and TypeScript, built by Vite into `crates/haul-web/ui/dist`, which haul-web embeds. Git keeps the built files, so `cargo build` and `cargo install` still need no Node; CI rebuilds them and fails when they no longer match their sources. The page's types for the state and settings are generated from the Rust ones with ts-rs, so a change in the engine's state breaks the UI's build instead of the running page. The page only lays out what the engine derived.

## shadcn look

The UI uses shadcn/ui components, copied into `ui/src/components/ui` and styled with Tailwind: neutral colors, Geist, Lucide icons. The window has a sidebar with the lists, the download folder and the pages; a header with the title on the left and the commands on the right; a status bar. It replaced a Windows 11 Fluent look because its user prefers this one, and the same page serves headless users in any browser.

Color says what a download's state is, and only that: blue runs, green is done, amber wants the user, red failed, grey is paused or waiting. The sidebar's counts sit in pills of those colors (Active only while something downloads), so the lists that need the user stand out; Wrappers, a source rather than a state, turns amber or red only when one of its wrappers waits for the user or failed.

A download that needs the user is a row of its own, tinted amber, with what the host wants at the end of its host line and one button where its bar would be: **Open here** in the desktop app, the page itself in a browser. The other ways (the page in the system's browser, pasting a link, trying again) are in that button's menu, so ten such downloads are ten rows, not ten boxes. The list never scrolls sideways: a row's columns wrap instead.

Each thing that needs attention is shown once. A download that needs you is flagged by its own row, and its count rides on **Needs you** in the sidebar (the desktop app also sends a notification); the bars above the list are kept for state that affects every list: paused downloads (only while the pause holds a download back; with nothing waiting, the status bar alone says Paused), a settings file with an error, a lost connection. The status bar has the speed, the counts and what is left with when it should be done, so the header carries no summary of its own.

The theme follows the system unless the user picks one; the choice is saved in `config.toml`, so the window frame can match it from the first paint.

## Local API

Loopback-only servers are still reachable from any page the user visits, so the API guards itself with `Host` and `Origin` checks and a framing ban ([HTTP API](api.md) has the details). There are no tokens to manage, and scripts without an `Origin` keep working.

## One settings file, two editors

Every setting lives in `config.toml` and can also be changed in the app. The app writes into the file with `toml_edit`, which keeps the user's comments and layout (a cleared value is commented out, not deleted, so its explanation stays). A file that disappears while Haul runs leaves the settings in effect because some editors delete the file before they write it anew, and falling back to the defaults for that moment would drop the proxy and move the download folder. There is never a second store that silently overrides the file, per-host route choices included.

Account secrets are part of the settings, but they never ride the state stream that every open view receives: the settings view fetches them separately when it opens. Values an environment variable sets cannot change in the app, since the file would not win anyway.

## Retries

Errors are sorted by what retrying can achieve. A dead link or a refusal fails its mirror at once, so the next mirror takes over without delay. A 403 while other downloads from the same host are running is different: that is the host taking no more at once, as pixeldrain does, so the download waits for a slot instead of failing; the two-second gap after a transfer gives the host time to count the finished one out. Network trouble is retried on the same mirror because the host usually comes back and the bytes already downloaded are kept, and an attempt that got data in starts the count over so a flaky connection or a change of network does not use up a mirror. Failures fade with a ten-minute half-life so one bad minute does not exile a host for the rest of the session. Failed downloads are tried again because hosts that are down tend to come back and the cost of another attempt is small. A wrapper's retry is unwrapped at once, as when it was added, rather than through the queue: its files only wait for the user, so it should neither take a download's slot nor wait behind them, and until November 2026 it sat as **Unwrapping** for as long as downloads held every slot. A row that failed before a restart counts as looked up, since only rows queued as Haul starts are looked up then: a wrapper or a file with no name came back waiting for a lookup nobody would make, and its retry never ran. A paste Haul read itself that lists no links counts as gone, as one passed in the desktop app always did, so neither is tried again on a timer.

## Choosing among mirrors

A preferred host that is only busy is waited for, since a user who stars a host (often one they hold an account with) wants the file from it; one that is cooling down or has failed for the file is passed over, so a preference never stalls a download for good.

Preferred hosts are tried in the order the user gives them, and the **Hosts** view changes that order two ways: dragging a preferred host's card by its grip, and the arrow keys on the focused grip. Up and down buttons on every card did the keyboard's part before, and read as clutter beside the star, the settings and the switch; a touch screen, which cannot drag, now has no way to reorder. Both send the whole list at once (`POST /api/preferred-hosts`), so the order on screen is the order saved; the star still adds a host at the end or takes it out.

Speeds come from real downloads. Haul does not test mirrors by downloading a piece of each: file hosts count every download start toward free-mode limits and wait timers, so a test can cost the real download. Going on from a mirror in the middle of a file is checked first, as [Leaving a host that slows an address down](#leaving-a-host-that-slows-an-address-down) says: resuming one from the other's offset unchecked would corrupt a file silently when the two hold other bytes.

## Files already downloaded

Hosts' checksums could prove more than name and size, but only by reading the file on disk in full: doing that for every match, four at a time, left a hard disk full of 5 GB parts seeking between them for minutes. Name and size decide by default now, and the checksum comparison is opt-in, one file at a time. Checksums come only from answers Haul already receives. rapidgator, nitroflare and 1fichier publish one too, but only through a separate file-info request per file, which can be added once it can be tried against files of our own.

## Removing downloads and host folders

A removed file goes to the Recycle Bin rather than being deleted, so a slip can be undone. Only the remove button of a finished download does that: **Clear completed** never touches files, because one click there would empty a folder of finished work into the bin. A file that cannot be moved (open in another program, say) keeps its row, so the user sees why and can try again. Files that older versions had megatools download are left alone, since Haul only knows the folder they share with other downloads.

A host's folder is decided when a file finishes, by the host that delivered it: a file merged from several mirrors goes where the mirror that won sends it, and a changed folder applies to downloads already running. Folder names are cleaned like file names and cannot climb out of the download folder.

## Installing for one user or for everyone

Tauri's NSIS installer offers both with the standard MultiUser support, which runs at the highest privilege the account has, so an administrator sees the UAC prompt as the installer starts, whichever mode they then pick. An existing installation's mode is preselected, so updates stay where they are. Haul's data lives in each user's profile either way, never next to the program.

## Updating over an older version

Tauri's installer recommends uninstalling an older version before installing, with that option preselected, so an update ran the old uninstaller first. Haul replaces its program files in place and keeps its data elsewhere, so uninstalling first only costs time. `crates/haul-desktop/windows/installer.nsi` is Tauri's installer template with that page skipped for updates, which install over the older version as **Do not uninstall** did. Reinstalling the same version, going back to an older one and replacing a version installed from the `.msi` still show the page. The template comes from the Tauri CLI version the release workflow uses and changes with it.

Haul looks for its own updates on GitHub (the latest release of `lordsilver/haul`, after start and every hour, unless `check_updates` is off, and whenever a person asks in **Settings**) rather than with Tauri's updater, which needs its own signing key and an update manifest in every release. The desktop app downloads the new setup program, checks it against the digest GitHub gives for that file, runs it with `/P /UPDATE /R` (progress only, install over this version, start Haul again) and closes; the installer is the same one a person downloads, so there is one way to install and one to check.

## The data folder on Windows

Haul follows Windows' per-user convention: a per-user install puts the program in `%LOCALAPPDATA%\Programs\Haul` and the data folder is `%LOCALAPPDATA%\Haul`, as other apps do (Zed, for one). Both are Local, not Roaming: the settings belong to the machine (download folder, router, proxies), so roaming them gains nothing. Tauri would name WebView2's data folder after the app identifier, so the desktop app points its own folders (`appDirectoriesOverride`) and the main window's browser data (`webview\main`) into the data folder, and no folder anywhere carries the identifier. A per-user install already went to `%LOCALAPPDATA%\Programs\Haul` (MultiUser.nsh's default for an installer that offers both modes); the uninstaller's option to delete the app's data now removes `%LOCALAPPDATA%\Haul` (a `Haul:` comment in `installer.nsi`). On Linux the data folder is `~/.local/share/haul`.

## Browser hand-off and proxy routing

Haul uses public APIs, guest tokens, the user's own accounts, and the pages themselves once their gates are passed. The browser hand-off lets the desktop app catch a download the user starts in its own browser window when a host page requires interaction. That window goes through the same proxy as the downloads (by way of a local, credential-free SOCKS5 bridge, because browser engines cannot pass proxy credentials), so opening a page does not reveal the real address that the proxy hides.

## Reaching the user when a host waits

Interactive host steps should be short and waiting downloads visible, so the status bar counts what needs you and goes there, and a click on the desktop notification lands on the waiting list. A toast for each download entering **Needs you** was tried first; with a page's pastes passed one by one it became a stream of toasts naming addresses, so the steady count replaced it. When exactly one download waits, its page opens right away, since that is what the notification asked for, and a single link pasted then is taken as that page's final link rather than a new row.

## A default preference for pixeldrain

Mirrors are not equal: pixeldrain hands a file to its API without an account or a browser step, mega.nz serves a free file at full speed up to its transfer allowance, vikingfile's page passes by itself in the desktop app, and megaup.net's does too once the desktop app presses its buttons (about 9 MB/s on a test in November 2026, where 1fichier gave the same file at 1 MB/s), while other hosts need an account, a browser step a person takes, or a paid tier, and some allow a free download only every few hours. `preferred_hosts` therefore starts as `["pixeldrain.com", "vikingfile.com", "mega.nz", "megaup.net"]`, so a file with one of those mirrors starts there and waits for it when it is only busy, exactly as for a host the user stars; the measured-speed order still decides among the rest. Taking the last preferred host out writes `preferred_hosts = []` rather than leaving the key out, because a missing key reads as the default and the preference would come back. The **Hosts** view lists every preferred host, reached or not, so the default can be seen and unstarred before Haul has used pixeldrain at all.

## Wrapper pages resolve on their own, and their files wait

A filecrypt.cc or fileguard.cc link wraps one set of files on many hosts. fileguard.cc's gate is a proof of work rather than a captcha, so Haul solves it itself; filecrypt.cc's is answered too, as [its own decision](#filecrypts-checkbox-is-answered-without-a-browser) explains, and waits for a person only behind a password or when filecrypt.cc turns the answer away; the `.dlc` a person's browser then hands back is fetched and read through the JDownloader key service like any dropped container. A `.dlc` link handed back stays beside the page it came from, as any link handed back does, so when it fails the page is asked for again.

A wrapper is a source of files, not a download, so it lives in a section of its own and its files never start on their own. A set of files behind one wrapper is often in many parts on a dozen hosts, most of them needing an account, a person or a paid tier, and starting all of them at once filled **Failed** and **Needs you** with rows that were only alternatives. So a wrapper is unwrapped the moment it is added, its files join the list not started, and the user picks what to start and what to remove; the wrapper's own trouble (a gate for a person, a dead link) shows in **Wrappers**, not among the downloads.

A file is one row with every host as a mirror, so one host failing is a failover, not a failed download. fileguard.cc lists each host's links in the same order, so the n-th link of every host is the same file; when the hosts list different counts, or a file's links disagree on its name, the links fall back to matching by name. A link the queue already holds keeps its row, state and turn, and the wrapper's links join it as mirrors.

Every link of a fileguard.cc vault shows the same page, and a burst of solves from one address was refused (HTTP 403), so a vault is added and solved once, solves run one at a time, a solved vault is read without a new solve, and a refused solve is tried again later rather than handed to a person who could do no better.

## filecrypt's checkbox is answered without a browser

filecrypt.cc's gate first waited for a person, because a replay of its proof of work alone was turned away and a real browser passed. Reading the widget's scripts showed why, and that a browser is not needed: next to the SHA-1 proof of work, the page posts what its automation checks found and a report of the visit (pointer, click, canvas, graphics, audio, fonts, screen), encoded but not encrypted. Tried against the live site, the answer is accepted whenever no automation check is flagged and the report holds the pointer's moves and its click, and only then; the user agent, the request headers and every fingerprint can say what they are. So Haul works the proof and sends exactly that: no automation found, the moves and click a person makes on the box, its own user agent, and "not available" for everything it has no browser for.

An embedded browser would also pass, at the cost of shipping or driving one for a page Haul can answer in a few requests; a browser extension, JDownloader's way, would tie Haul to the user's browser. The answer depends on filecrypt.cc's scripts, which can change: when they do, the answer is turned away and the container waits for a person, as before, so nothing breaks worse than it was. The solved page's Click'n'Load data carries its key, so the links are decrypted locally instead of through JDownloader's key service, which the `.dlc` still needs.

### A container per host is one archive

A release page often links one filecrypt.cc container per host, and each host lists the parts under the name its uploader gave them there: an id on one (`a1b2c3.part01.rar`), a shortened name on another, the full one on a third. Merging by name then gives one archive per host, and the parts would not even unpack together, since an archive's parts on disk must share a name. So when a container's files are an archive's parts 1 to n, and another container of the same page under the same title brought parts with the very same numbers, part k of each is taken as the same file: its links join that row as mirrors. Every part takes the name that says most of the ones the files have (a name over an id, then more words, then the longer one), and a host's own name for the file no longer replaces it when the file is looked up.

Until November 2026 the parts took the containers' title where it could be a file's name. Titles turned out not to name the files: unrelated sets can share a generic one such as `Folder`. Two sets with the same part names and split size would then look like one file to Haul, so a part could be skipped as already downloaded, the sets shared one card, and the second set landed as `Folder.part1 (1).rar`, which does not unpack. When every name is an id, the parts now keep one on disk, and only the card shows the title.

A shared title and part count can still be two sets of files, and merging those would mix their parts. So since November 2026 the merge also compares the size the filecrypt.cc table shows for each part, and stays apart when one differs by more than 2%. Sets split alike differ only in their last part, which is why every part is compared. Those sizes are rounded and can be missing (`n/a`, a `.dlc`), and then the merge goes by title and numbers alone: two separate cards cost a download twice at worst, while a wrong merge breaks the archive, so only a clear difference counts. They are kept apart from the file's real size, which comes from its host.

### Behind Cloudflare's check, a browser passes it and Haul answers the rest

In October 2026 filecrypt.cc put Cloudflare's browser check in front of its containers, so Haul's requests got `403` with `cf-mitigated: challenge` and every container waited for a person. Edge, passed out of sight, gets past the check by itself, but then shows filecrypt.cc's own checkbox, which wanted a person in a driven browser: a click from the page's scripts is marked as not a person's, and a real click through DevTools left the widget working without an answer. Tried against the live site (Oct 25 2026), a plain request carrying the `cf_clearance` cookie Edge got is answered with the real page (`200`, the checkbox Haul already answers), with Haul's own user agent, curl's or Edge's alike, over Haul's TLS as well as a browser's.

So when the desktop app passes a page Haul's own code reads (a wrapper's or a host's, not a page whose file the browser itself takes), the pass ends as soon as the browser is past the check, and Haul's requests to that site carry the cookies Cloudflare set (`cf_*`, `__cf*`; none of the site's own) and the browser's user agent. The page, and the site's other pages waiting for a pass, are then read by Haul as before the check. One turned away again after a clearance is passed the usual way, without handing a clearance over again until it is tried again by hand, so a clearance that does not hold (another address, say) asks the person rather than going round. The clearance and the user agent live in Haul's memory only; the site's Edge profile keeps the clearance for the next start.

By November 2026 the clearance held only with the user agent it was given to: tried against the live site (Nov 1 2026), a plain request carrying Edge's `cf_clearance` got the real page with Edge's user agent, from Windows' curl and from WSL's alike, and `403` with Haul's own or another Chrome's. Every container was turned away after the hand-over and went on to Edge, where filecrypt.cc's own checkbox wanted a person; with Edge's user agent, Haul answered the checkbox and read the container. Sending the browser's user agent to that site alone keeps Haul's own user agent everywhere else.

Haul's own user agent is fixed, not a setting. On Nov 6 2026 the home page and a made-up file page of every supported host and wrapper answered it exactly as they answered a current Edge's: the same status and the same page, and Cloudflare's check on buzzheavier.com, fileguard.cc and filecrypt.cc turned both away alike. The check tells Haul's requests from a browser's by more than the name they give, so a browser's name would buy nothing and would claim what the requests are not.

What tells them apart was measured on Nov 7 2026, from the home line, against every supported site with nine clients and made-up IDs. It is the TLS handshake, and on one site only: buzzheavier.com let current Chrome, Edge, Firefox and Safari handshakes through where Haul's (reqwest with rustls) and curl's were turned away, whatever user agent either sent. It did so per request, though: the download request Haul's resolver sends passed Haul's own handshake every time, and only the home page, a file's page and the bare download address turned it away. filecrypt.cc (whose check says it is a `precursor_interstitial`), zpaste.net, fileditchfiles.st's file addresses and fileguard.cc's login page turned every client away alike; fileguard.cc's home page is only turned away because it redirects to that login page, and its file pages are not. The other twenty sites answered every client. So Haul keeps reqwest: `wreq`, which copies a browser's handshake, gave the same answers on the requests Haul sends, for twice the build and a BoringSSL build on Windows. If a site starts turning Haul's handshake away, `wreq` can be added for that site alone. Meanwhile a buzzheavier download request that is turned away counts as a check a browser passes, not a missing file, so the desktop app passes it and hands Haul the clearance, and a row behind a check names the kind of check its page says it is.

On Nov 2 2026 filecrypt.cc answered Haul's requests, past the clearance, without its checkbox: the page asked for a picture puzzle instead (drag the pieces into their holes), which Haul cannot answer. Edge, passed out of sight, was shown the container's links straight away on most containers of a page (four of seven), and the puzzle on the rest, which the person solves in Haul's window. Either way the browser was on the solved page and nothing took it, so every container waited for a person, and one who solved the puzzle still had to find the `.dlc` button. The page's script now hands over the solved page as soon as it shows the links, in Edge and in Haul's window alike: the parts Haul reads (the heading, the link table's rows and the Click'n'Load data), with the `.dlc` link beside them. Haul reads them as it reads a page it solved itself. Handing back only the `.dlc` worked too, but left a host whose links carry no name (gofile) as rows of their own: the `.dlc` named none of its files, where the page's table names every one, so the files of seven containers took 27 rows rather than 14. The `.dlc` stays the fallback for a page without Click'n'Load data.

Tried against the live site on Nov 4 2026, that gate turned out not to need a clearance to reach Edge. Haul sent a container to Edge only when Cloudflare's check turned it away, so once one container had handed over a clearance, every other container of the run was read directly, met the gate and stopped under **Needs you** within a second, while Edge would have been let through. Any gate Haul has no code for now goes to Edge, with no clearance taken from that pass, since Haul would only read the same gate again.

The same runs showed filecrypt.cc answering `404` "Not Found" to every container asked, from a fresh Edge profile, right after Cloudflare's check; containers that had opened minutes earlier included. It lasted beyond the three hours it was measured for. A plain request with the same cookies is redirected to `/404.html`. A deleted container cannot be told apart from this, so such a pass ends at once rather than wait out its time for nobody, the row says both possibilities, and it fails for now, not for good: unlike a file a host says is gone, it stays due for its automatic retries.

It is not a refusal of the address, as first thought: later, on the same line and within the same minutes, the same containers opened in an Edge profile in use for days and answered "Not Found" in a fresh one, with debug mode on or off. What sets the two apart is not known yet; the row now says the site may be refusing the browser.

A page's site can answer a form with the file itself, as ddownload.com does since a page change noticed on 2026-11-05: Edge saved it to the person's Downloads folder out of sight, used up the free download, and Haul waited for a link that never came. Every page pass now tells Edge to report files instead of saving them (`Browser.setDownloadBehavior`, `Browser.downloadWillBegin`), and Haul downloads the reported address itself, so it can resume and show progress.

## The in-app browser keeps to the host's site

Host pages carry ads that act on a click: they send the page to an ad's site, or open the wanted page in a new window and send this one to the ad. The in-app browser has no tabs and refuses pop-ups, so that left the person on an ad with no way back. Measured on the hosts of one set of files, each page pulls 0.3–0.7 MB from 5 to 14 ad sites, on random domains that rotate, so a block list would be stale within weeks. The window therefore keeps to the host's site instead: a page from another site that replaces the host's is sent back (back in history first, which keeps a countdown that has run), to the wanted page when an ad opened it in a new window; a new window on the host's own site loads in place unless the page goes on by itself; downloads, which replace no page, are untouched. The host's site includes wherever its first page lands, since some hosts serve their pages from another domain, and a site the page keeps going to by itself is let be after three times within half a minute. A wrapper's page is held tighter: Haul reads it itself once a person is past its gate, so it has no flow of its own off its site, and its ads arrive on a new throwaway domain each load (one container page linked five different ones in a day), which sending back and remembering would not keep up with. Once its first page has loaded, its window is refused any other site before it loads, but for a host or wrapper Haul knows (a link the person follows) and a file. Before that it went where the ads sent it, which left a person who opened a gated container on an ad page and never on the gate. A page that lists links, on a site Haul has no code for, still goes where it will. A site a window was sent back from has shown itself to be an ad's, so while Haul runs no window loads a page from it again: the navigation is refused before anything is fetched. Only a page that loaded marks a site so, never a download, and a site later let be as part of a host's flow is taken off.

Ads also lay a layer over the page, an ad's frame or an invisible sheet above everything, so the first click lands on the ad instead of the button under it. A script the window runs before the page's own takes such layers off as they appear: one above everything that covers much of the window and holds an ad's frame or nothing at all. A captcha floats above the page the same way, so a layer holding a captcha provider's frame stays.

## Pages come compressed, files as stored

Resolvers read whole pages, and some are large: a filecrypt.cc container is 660 KB of HTML, 169 KB gzipped. Haul asks for gzip, which costs one small crate beside the deflate code already in the build, and decompresses as it reads. A file is asked for uncompressed (`Accept-Encoding: identity`) on every request that downloads it or reads its size, because resuming counts the stored bytes and a compressed answer would report another length.

## Hosts can be switched off

A set of files behind a wrapper sits on a dozen hosts, and some of them only ever ask for an account, a person or a paid tier. The user chooses which hosts Haul may use at all, next to the order of the preferred ones: a host switched off (`disabled_hosts`) is never picked, probed or asked for a person, so its links stay in a file's row without costing anything. A file whose links are all on hosts that are off fails with that reason rather than waiting for nothing, and switching one of those hosts back on starts it again. Switching a host off takes it out of the preferred hosts, and starring one switches it back on. This is the deny list the first wrapper review left out; the owner asked for it.

A host whose free download is too slow to be worth having starts off, at the owner's word (2026-11-06): ddownload.com, whose free download ran at a flat 30 KB/s after its one-minute wait and Cloudflare check, on two machines. rapidgator.net starts off too, at the owner's word the same day: its free download is a wait and a reCAPTCHA for a person on every file. Their links still join a file's row, and switching one on in Hosts makes it a host like any other. Off hosts sit at the end of their group in the Hosts view, below those used only when no other host has the file.

## Hosts without their account are used last

gofile.io, rapidgator.net and nitroflare.com give no decent download without their account: rapidgator and nitroflare make a person solve a captcha for every file, and gofile can only be read by passing its page in a browser, which only the desktop app does by itself. From 2026-11-02 they were off until their account was set, at the user's word, and from 2026-11-05 a wrapper's file only on such a host was kept out of the lists. That left files nothing could fetch: a set of parts sat two short while their only remaining copies were on gofile.

On 2026-11-06 the user settled it the other way: the account is optional, and these hosts are on. Without its account, such a host is used only when no other host that isn't switched off has the file, and only when its free download would cost the person a step (`Known::last_resort`): rapidgator and nitroflare always, gofile only where pages aren't passed out of sight, since in the desktop app its page needs nobody. So a file on pixeldrain and rapidgator never asks for a rapidgator captcha, and a file only rapidgator has asks for one under **Needs you**. A host another host is cooling down for doesn't count as "no other host": the file waits for that one rather than cost a captcha. `accountless_hosts` keeps its meaning for one that should be used like any other without its account. 1fichier.com stays an ordinary host, since its free download is fast once its captcha and short wait are past; pixeldrain gives a file without an account. Switching any of these hosts off works as for any host.

## A log kept over time, and each download's own history

The first report carried the end of the log as text, notable events only, and only the desktop app wrote one. A report has to show how a download got where it is, so `haul.log` is now JSON Lines (time, level, message and fields such as the download and the link), written by the desktop app and the server alike, kept across runs up to 10 MB a file with five older files. Every download also keeps its last 40 events in memory, debug ones included whatever the log level, and the report carries them.

Since November 2026 the log itself leaves out the part of a link after `#`, not only the report: that part holds mega.nz's keys, and a log is a file people open and send. A log written before that keeps its keys until it rotates away, so the report strips them from the logs it carries too, line by line, as it does for `timeline.txt` and `report.json`. Queries stay in all three: 1fichier names the file in its query, and the three should agree. A **Detailed log** switch writes Haul's debug events to the file too while it is on; it applies at once, and `RUST_LOG` still decides when set. OpenTelemetry export was left for later: end users have no collector, and the file is what they can send.

## Many proxies, each its own address

Hosts limit what one address may do: pixeldrain takes five downloads at once and serves 6 GB a day at full speed, then 1 MiB/s for the whole address. One proxy only moves that limit to another address, so Haul takes a list of them (`proxies`, beside `proxy`) and keeps a host's slots, the limit it showed, the waits it asked for and its quota per address. A download takes the address with the fewest of that host's downloads, preferring one the host has not slowed, and keeps it until it ends: a resume or a session that changed address halfway would be refused. Speeds and failures stay per host, since they describe the host. The user's own line can be one more address (`proxy_with_direct`), which shows their real address and so is off by default, and a proxy that gives each connection another address gets a new connection per download (`proxy_fresh_connections`). Lookups and gates use the first proxy, as they did. No proxy service is assumed: anything that speaks SOCKS5 or HTTP fits, so a VPN subscription's SOCKS5 servers can be reused rather than buying another service.

## One description per host

What Haul knew about a host was spread over a list of names, three `match` statements and a pixeldrain case in the engine, so a second host with a daily allowance would have needed another special case. Each host is now one entry of a table (`hosts::KNOWN`): its names, its code, the accounts it takes, what a free user gets where it was measured, and whether it reports how much an address has left. The engine asks the table: a known free limit holds from the first download rather than after a refusal (and an account lifts it), and every host that reports an allowance is asked through each address. Limits nobody measured are left unknown and still learned from refusals.

The code still had a `match` per thing a host can do (resolve, look up, unwrap, name its wrapper, read its page, tell its allowance), and a host left out of one silently got the generic behaviour. Since November 2026 each entry points at the code behind it (`hosts::sites`), which says once what the site does and keeps the default for what it does not; the dispatch asks the entry. A host's other domains are its entry's names, and a test keeps the aliases and the table in step.

## A new address from the router, found and tested by Haul

Hosts limit an address, and most home lines get a new one when the router redials, so a redial is a proxy-free way past a slowed or waiting address. Download managers have offered that for long, but left the setup to the user: pick a router, record or import a script, try. Haul finds the router itself (an SSDP search for an Internet Gateway Device, and a FRITZ!Box's known addresses), asks it to redial over UPnP, which needs no login where the router allows it, falls back to TR-064 with the router's login where it does not, and checks that the line came back with another address. A command of the user's own covers anything else. Redials cut the line for the whole home, so they are off unless switched on, come at most every ten minutes, only when the user's own address is what holds a download back and no proxy can take over, and stop for good when a redial brings the same address back, as DS-Lite and shared-address lines do. The router is only looked for once the feature is on or its settings are shown.

## Connections in one place, integrations in one shape

Proxies, the router and VPN services all decide what downloads go out through, so they share a **Connections** page instead of sitting among the other settings. They also share one shape underneath: a source of addresses (the proxy list, a VPN service's servers) only adds exits to the pool, which the engine treats alike, and a source of new addresses for the line itself (a router, a command) only answers "get a new one". A VPN service is an integration only for finding its servers: NordVPN publishes its SOCKS5 servers and their load, so the user gives its service credentials and a number, and Haul keeps the least loaded ones in the pool, refreshed hourly. Another service is another list, not new engine code.

## Hosts' own pages sign for Haul, out of sight

Some hosts hand their links only to their own website's code: vikingfile behind Cloudflare Turnstile, gofile behind a request signature from a secret it rotates, where a request signed with a retired secret gets the address banned. Haul does not imitate that code today (it holds no copy of their secrets and embeds no JavaScript engine); instead the desktop app opens the host's page in its own browser, off screen, and a small recipe per host (`handoff.js`) reads what the page receives (vikingfile's download button, gofile's folder listing) and hands it to the engine, or says the file is gone. A page that still wants a person after its time waits under **Needs you**, to be opened in Haul's own window; the page passed out of sight never comes on screen. Each host's capabilities stay in one table (`hosts::KNOWN`): the accounts it takes, whether it gives a decent download without one (`needs_account`), what a free user gets, whether it tells its allowance, and whether its page passes this way (`page_passes`). A host that needs an account is off without one until the user switches it on (see [Hosts that need an account start off](#hosts-that-need-an-account-start-off)); only then is gofile's page passed this way.

### A page's own word on its host's limit is the host's cooldown

ddownload allows an address one free download about every two hours, and while that holds its page's button only opens a payment dialog. A person can do nothing there, so nothing about it belongs under **Needs you**. The page states the seconds left, and since the limit is the address's rather than the file's, they become the lane's cooldown (`page_later`), not one wait per row: every row on that host sees the same wait, the Hosts view shows it, a new address from a redial ends it (with redialing on its own switched on, a wait this long on the line's own address asks for one, as any other host's does), and no pass opens a page meanwhile (`pass_held_until`, which `pick`, the views and the desktop app's `page_passes` all ask). Only the lane the pass goes out from is on hold, as a limit on one address leaves the others free. A row with another usable mirror goes on to it, a host Haul has no code for included, and one with only such pages waits with the row's usual countdown; a row with a page only a person can do beside it still waits for that person. A number that comes from a page counts for a day at most, so a wrong one stops a host no longer than that. The same hold now applies to any wait a host asks of the address (a 429 to one of its links), which otherwise left a row due for a pass showing under **Needs you** until it ended.

### Pages that wanted a person are passed again

Turnstile is not all or nothing: one part's page wanted a box ticked while ten others of the same set passed in the same minutes, and that part then sat under **Needs you** for hours. A page the desktop app passes by itself therefore gets the same automatic retries as a failed download (`retry_failed_minutes`, `AUTO_RETRIES`, the two sharing one count), since a try costs only an off-screen browser for a minute, and the first page to want the person still tells them. What comes of those tries tells nobody (`page_retrying`); for the time a try runs the row shows as passing, because the desktop app ends a pass whose row is no longer doing so, and between tries it stays under **Needs you**, where **Open here** works and the row says when the next try comes. Keeping the row under **Needs you** during the try as well was left out: it needs a second state for what the desktop app and the views read as one.

The person comes first. **Retry** starts the count over, a link handed back ends it, and a page open in Haul's own window holds the timer: the engine does not know about windows, so the desktop app's loop tells it every few seconds (`page_with_person`), which also returns a try that just came due without counting it. A page that settled past its checks with no links Haul takes is not passed again (`page_needs_click`): the same page would show the same, and only a click on it leads on.

### Which browser passes those pages

Measured on Windows 11 against vikingfile's Turnstile, 36 interleaved trials (fresh profile each, off-screen window, on the line and through a NordVPN server): Edge, Chrome, CloakBrowser and WebKitGTK passed 6 of 6 each without anyone ticking anything (median 3.6 to 4.6 s on the line, 5.8 to 6.7 s through the VPN); Cromite and the app's own WebView2 window got the box 6 of 6 each. WebView2's box was not the off-screen window nor Haul's scripts (both tested): Cloudflare tells an embedded WebView2 apart from Edge. So on Windows the desktop app passes such pages in the Edge that comes with Windows (or Chrome), off screen with a profile of its own, driven over DevTools only to add its page scripts and read what they leave (`chromium.rs`); `Runtime.enable`, which automation is told apart by, stays off. The DevTools port is one Haul picks and names: started with `--remote-debugging-port=0` (the browser picks), the same Edge got the box 4 of 4 times, with a named port, low or high, it passed 8 of 9. CloakBrowser passed as well but brings a 562 MB download and a company's licence; a click on the box (as Turnstile solvers do) did not pass in the browsers that got it. Linux keeps WebKitGTK, which passes.

## Extracting archives inside Haul

Archives are unpacked by Haul itself rather than by an installed 7-Zip: an archive's parts can be RAR, 7-Zip or zip whatever their names say, and an extractor that comes with Haul handles all of them on every machine. RAR goes through RARLAB's own unrar library (as `unrar_sys` vendors it), 7-Zip through `sevenz-rust2` and zip through the `zip` crate. The `unrar` crate around the library was left out: its callback for the next volume reads 2048 characters from a shorter name, past its end, on every archive in volumes, and `unrar_sys` lays out the library's structures without the byte packing `dll.hpp` gives them, so Haul declares those structures itself and a test pins their offsets to the header's. Which parts make an archive follows the forms JDownloader's extraction recognises (its `ArchiveType`), including telling from the numbers which part is missing, so the archive waits for it rather than failing to unpack. JDownloader opens a zip split into `.z01` pieces with a separate library, Zip4J; Haul reads the pieces as they are and adds a copy of the central directory with each file's place made an offset into all of them, which is all that differs from one zip, so the `zip` crate reads it without the pieces being written again. Old-style RAR volumes would reach `name.z00` after 2600 parts, so a `.zNN` name is taken for a zip's piece.

Extraction runs one archive at a time and writes into a hidden folder beside the first part, moving each entry out under a free name only once all of it is unpacked, for the same reasons downloads never overwrite a file and partial files stay out of sight. It is off by default because it doubles the disk space an archive takes until the parts go; the parts go to the Recycle Bin rather than being deleted, as removed downloads do, and only after an extraction that succeeded.

## The engine works out what the views show

The web UI renders what the engine's state says rather than deriving it: which list a download is in, the host it is shown under, which buttons it has, an archive's parts summed up, which wrappers share a card, the counts of the navigation pane and the status bar, how the hosts group, and the pool of addresses in words come worked out in each state (see [HTTP API](api.md)). The rules then live once, in Rust, with tests beside them, where the page's JavaScript has no tests; a script reading the API sees what the window shows; and the page does less on every state it receives. The page keeps what belongs to the browser alone: the selection, dragging, which archives are opened, the theme, dialogs and toasts, search as you type, and the wording of numbers (sizes, durations).

## The UI routes itself, without TanStack

The UI's views are ten flat addresses in the hash (`#/all`, `#/attention`, `#/wrappers`…) and `#/add/<links>`, which opens the Add dialog filled in. A file of about fifty lines handles them (`ui/src/lib/route.ts`). Considered in October 2026:

- **TanStack Start** is a full-stack framework. What it adds over a React app is server rendering, server functions and server routes, run by a JavaScript server. Haul has none: the Rust engine serves the UI and owns the API in the server and in the desktop app alike, whose window loads the engine's page. Start would bring its build and conventions with none of what it is for, and server functions would put logic in JavaScript next to the engine, which the views must not hold ([above](#the-engine-works-out-what-the-views-show)).
- **TanStack Router**, the client-side router Start is built on, would work in both apps with hash history. But what it offers is already here or unused. Links are already typed: `go()` takes only a view's name. Nothing lives in the URL besides the view: search, selection and expanded rows are component state. There is one layout, so nothing nests. Loaders would be a second way for data to reach the views, next to the engine's one stream. And code splitting gains nothing in a UI compiled into the binary and served over loopback. It would cost more script than the page needs (the whole UI is about 160 KB gzipped; the router's own share was not measured), more churn in the built UI kept in git, and care with `#/add/<links>`, which it would read differently.

The addresses are a contract beyond the UI: the desktop app opens `#/attention` or `#/wrappers` from a notification and `#/add/<links>` for files dropped on it (`haul_web::WAITING_ROUTE`, `WRAPPERS_ROUTE` and `add_route`), and `#/add/` is published for bookmarklets and scripts (usage.md, api.md). A test checks Rust's routes against `route.ts`, and the type checker checks the lists against the engine's. Whatever routes the UI has to keep these working.

**What would change this:** state worth keeping in the address, such as filters, search or sort that survive a reload and go back and forth (`#/failed?q=…`), or a list beside a detail pane that the address selects (a download, a wrapper, a host). Typed, checked search parameters and nested routes are what TanStack Router is for. A single address with an id (`#/item/<id>`) still fits `route.ts`; a second or third, or a decision that every view should be linkable before such addresses are published, is the time to move. Start would only come into question if Haul ran a JavaScript server, which it does not plan to.

## Copied one-time links are not looked at

Clipboard watching looks at any copied web page for links, and looking means a plain GET. A one-time link (a sign-in, an email's confirmation, an unsubscribe, a password reset) can be used up by that GET, so a copied page whose path segments or query keys hold, as a whole word in any case, token, confirm, verify, verification, unsubscribe, login, signin, sign-in, logout, reset, activate, magic, otp, auth, callback or oauth is not looked at (`hosts::ONE_TIME_WORDS`, through `hosts::is_copied_page`). The scope is that lookup alone: links pasted into **Add**, dropped or in containers are added as before, and copied links to known hosts, files, wrappers and pastes are added as before. The user approved this restriction on 2026-10-24.

## Leaving a host that slows an address down

Many free hosts don't refuse a download past their limit: they let it crawl. ddownload held a steady 30 KB/s over the 70 seconds it was measured, and two 4.29 GB parts at that speed read as 31 hours left, while another host of the same set served other parts at full speed. Haul had one answer, `min_speed_kbps`, off by default and blind to the reason: a bare floor can't tell a host limiting this address from a slow line, from the user's own speed limit, or from a small file about to finish. So a transfer is watched from outside, once a second (`engine/throttled.rs`, the rules and every constant in `throttle.rs`), not in the transfer's own loop, because comparing it with other transfers and deciding what to do are questions about the whole queue, and a stalled connection sends no chunk to wake a loop.

**What counts as throttled.** All of these at once, each because of a way the others go wrong:

- Past a grace of 30 seconds, whose bytes count for nothing: transfers start slowly, and a host may burst and then settle, which would flatter the average.
- Slow as an average over a whole minute, so no single bad moment decides.
- Under 1.2 MB/s. That is "about 1 MB/s" set just above pixeldrain's 1 MiB/s for a slowed address, which is a throttle by the host's own word. A host far below its own normal counts higher up, up to 5 MB/s at a tenth of it. One still within half of its normal is just a slow host and is left alone.
- More than 10 minutes left at that speed. Moving costs a lookup, up to two minutes of a page's pass, and the next host's own grace, so a file done sooner stays. An unknown size counts as long.
- Not explained by the user's own speed limit: the limit is taken up (70% or more of it in use), or this transfer has at least half of its share.
- Not explained by the line: when transfers from other hosts on the same exit are slow at the same moment, nobody is blamed. Any other host running well proves the line is fine, through any exit. When the slowness outlasts 5 minutes and the line is known to do far better, it is no longer taken for the line, since otherwise two throttled hosts would clear each other for good.
- With nothing running to compare with, a host's own history decides (under a quarter of its normal), then what the line has shown on other hosts in the past week. With no history at all it waits two more minutes, and then counts only as unsure: enough to try another mirror, which costs little, not to hold other files back or cut the whole home's line for a new address. A line that is slow by itself, with every host under the slow line, loses nothing to this: the row says it is slow, and files start as before.

Normal is `HostStats::normal`, not the existing `ema`. `ema` follows a throttled transfer down to its speed in about ten seconds, so it can't say what the host usually does; `normal` learns only from whole windows above the slow line.

**What happens, in order.** First the host's lane goes on cooldown, unless another transfer on that lane runs well or the host only looks slow and the row stays: a row with another host that can take it doesn't start there or pass its pages, and the Hosts page's existing badge shows the wait. A row with nowhere else to go starts anyway, as the user decided on 2026-11-05: with one host there is nothing better to do than keep downloading from it, and other files carry on. This also stops a host that is always slow from leaving files idle for hours between downloads. The cooldown is 30 minutes, doubling to 4 hours while the host stays slow each time it is tried, since how long a limit lasts isn't known: a two-hour limit is found in three tries, each costing a minute and a half, while a shorter limit costs little waiting. A transfer that stays slow keeps its host's cooldown from running out; one that recovers ends it. A page that states the seconds still wins, as before.

Then, whichever comes first:

1. **A mirror that can take it now** (or the same host through another proxy or VPN exit, which is a new address for free): the transfer stops and the row goes on there. It has to have a free slot now, not be cooling, not be measured no better, and not want a person. A throttled download beats a row parked under **Needs you**, so a mirror only a person can use doesn't count, and the row says those mirrors are there. A row the user pinned with **Download from** stays and says so.
2. **A new address for the line**, when `reconnect` is on and the line is what this host is reached through. See below.
3. **Nothing**: it keeps downloading, since slow is still progress, and says why. The check runs every second, so a cooldown ending or a mirror coming free moves it then.

**Rows don't bounce.** A mirror left for slowness is cooling, so nothing returns to it until that ends, and the doubling makes each return rarer; even past its cooldown the row prefers another mirror that is free. A row with no host that can take it goes to one that only slows the address rather than sit idle, one that slowed it before first: with its other mirrors gone there is nothing left to bounce to. A wait a host asked for still stands. A page the desktop app can pass goes before that, which also fixes a row with a page to pass and a known host cooling down: it sat queued for the whole cooldown, and the page never got its turn.

**Draining before a redial.** `wants_new_address` had a gap that this feature would have turned into real damage: it looked at every mirror of every row, whatever that row was downloading from. A file running well on one host, with a mirror on a host cooling down, asked for a redial, and `hold_direct` then aborted that file. With throttling putting hosts on cooldown, the row that had just moved to a fast mirror would be cut off within 30 seconds. It now asks only about rows actually held back: one running on the host, or one all of whose hosts hold this address back. The order for a redial on its own is:

1. Not started while a download running well on the line can't be expected to finish within the limit: holding the queue for nothing helps no one, and the throttled row is still making progress. New files keep starting meanwhile.
2. New starts and page passes stop (`State::draining`). Downloads through a proxy aren't waited for, since a redial doesn't touch them.
3. Downloads on the line running well go on to their end. Slowed ones aren't waited for; they would take hours.
4. As they end, the existing `Engine::reconnect` runs: it stops what is left on the line, which is only the slowed ones, redials, and clears what was learned about the old address.
5. Everything goes again, the stopped rows resuming from their partial files.

Draining is limited to 10 minutes. At the limit Haul gives up on this redial rather than abort anything: the queue goes on, and it asks again after the usual 10 minutes between redials. A person pressing **Get a new IP** is not drained: they asked, and were told what stops.

A redial that doesn't help must not repeat, since it cuts the line for the whole home. When a host is still slow on the address a redial just gave it, it doesn't limit by address, and no further redial is made for it during this run.

**Partial data.** This section's decision replaces what [Choosing among mirrors](#choosing-among-mirrors) said about not switching mid-file. That was out of date: the code already resumed a failed mirror's partial file on the next one with a plain `Range`, unchecked, which throttling would do far more often, and sets split alike can share a name and an exact size. Now a resume on another host than the bytes came from asks for 64 KiB more than it needs and compares them with the end of the partial file. Hosts' data here is compressed archives, so bytes that agree at that point are the same file. The partial file is thrown away and the download starts over when the two disagree, when the host gives another total size, or when it ignores the range. Only those show another file: a link that has run out can answer any range with a 416, as one did after an update, so a 416 without a size that differs, or an answer that ends before the comparison, fails that attempt and keeps the bytes. So nothing is lost when the next host resumes and agrees, and all of it otherwise, and the row's history says how much. Checksums aren't compared here: two hosts rarely publish the same kind, and the overlap needs none.

**Which host a transfer belongs to.** All of this needs the row's host to be true, and it wasn't. A file handed back by a page was tied to no mirror (`pre_for: None`), and `set_direct` also cleared `failed`, so `pick` chose whichever mirror ranked first, a preferred one even if its copy had been reported deleted, and the handed file downloaded under that name. The row said the wrong host, that host's lane and speed took the numbers, and the file's folder came from it. A handed file now belongs to the page it came from, or to the mirror on its own host when it has one, and the transfer runs on that host's lane; a mirror marked gone stays out. Which page handed it over isn't said by the desktop app; Haul takes the one the desktop app's pass loop would have chosen by the same rule, the first the row has that may pass now.

**A setting, not a removal.** `leave_slow_hosts` (**Settings › Retries › Leave hosts that slow you down**, on by default) turns all of this off. `min_speed_kbps` stays beside it, because it does another job and removing it would lose an ability: it is the user's own hard floor, whatever the reason, and it fails the download when no mirror is left. The automatic behaviour never fails anything.

**What was measured.** In a run on real links on 2026-11-05, ddownload held 30 KB/s and the row moved to vikingfile about 90 seconds in. The join passed the 64 KiB check, and the archive part's own checksum matched across the whole 4.29 GB. On two new addresses in a row ddownload stayed at 30 KB/s, so that speed is its free tier and not a limit on the address. Haul then gave up redialing for it, as designed, at the cost of one redial that didn't help. The file's link kept working across the redial.

**What this can't know.** Real throttles have not been measured against these numbers beyond the one host. Two hosts throttling at the same moment take 5 minutes to tell apart from a slow line. A proxy that gives every connection a new address (`proxy_fresh_connections`) gets a cooldown like any other, though a new connection alone would do.
