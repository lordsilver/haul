# Testing the desktop app on Windows

Debug mode (`docs/debugging.md`) is the way in: a live stream of every signal, the insides, waits instead of polling, and a look into a page being passed. Read that page first.

Never touch the user's own Haul (the program in `%LOCALAPPDATA%\Programs\Haul`, its data folder `%LOCALAPPDATA%\Haul` or its queue): the test copy lives in `%TEMP%\haul-test` with a data folder and port of its own, and is stopped by its command line.

## A Windows build of a branch

The local `cargo xwin` build fails in unrar's C++ code, so build on CI (about 15 minutes) and take `Haul.exe` out of the setup:

```sh
~/.local/bin/gh workflow run release.yml --ref "$BRANCH"
id=$(~/.local/bin/gh run list --workflow release.yml --branch "$BRANCH" --limit 1 --json databaseId --jq '.[0].databaseId')
# wait for it (a Monitor until-loop on `gh run view $id --json status`), then:
D=$SCRATCH/build && rm -rf "$D" && mkdir -p "$D/x"
~/.local/bin/gh run download "$id" --dir "$D"
7z e -y -o"$D/x" "$D"/windows-installers/*setup.exe Haul.exe
T=/mnt/c/Users/$WINUSER/AppData/Local/Temp/haul-test && mkdir -p "$T" && cp "$D/x/Haul.exe" "$T/" && rm -rf "$D"
```

## Start, follow, act, stop

```sh
W="C:\\Users\\$WINUSER\\AppData\\Local\\Temp\\haul-test"
powershell.exe -NoProfile -Command "\$env:HAUL_DATA_DIR='$W\\data'; \$env:HAUL_PORT='8791'; \$env:HAUL_DEBUG='1'; Start-Process -FilePath '$W\\Haul.exe'"
WINCURL=/mnt/c/Windows/System32/curl.exe B=http://127.0.0.1:8791
TOKEN=$(tr -d '\r' < "$T/data/debug-token")
dbg() { "$WINCURL" -s -H "X-Haul-Debug: $TOKEN" -H 'Content-Type: application/json' "$@"; }
dbg -N "$B/api/debug/stream?replay=true" > "$SCRATCH/stream.jsonl" &      # everything, as it happens
dbg -d '{"text":"http://127.0.0.1:8799/guard/swap"}' "$B/api/add"
dbg -d '{"match":{"kind":"pass","event":"end"},"timeout":120}' "$B/api/debug/wait"
dbg "$B/api/debug/inspect" | jq '.desktop, .engine.items'
powershell.exe -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { \$_.CommandLine -like '*haul-test*' } | ForEach-Object { Stop-Process -Id \$_.ProcessId -Force -ErrorAction SilentlyContinue }"
```

- WSL cannot reach Windows' loopback; Windows' own `curl.exe`, started from WSL, can, and its output comes back to WSL. PowerShell's `Invoke-RestMethod` cannot stream.
- Start a fresh data folder (`rm -rf "$T/data"`) for a first-run test; the Edge profiles under `data/webview/chromium/<site>` (and Chrome's under `data/webview/chromium/chrome/<site>`, for a pass Edge kept closing) carry Cloudflare clearances between runs.
- A link already in the list is a duplicate, query string or not: give each try a fresh address (`/guard/stuck-2`).
- The Edge processes of the test copy carry `haul-test` in their command line; count them with `Get-CimInstance Win32_Process -Filter "Name='msedge.exe'"`.

## Pages passed out of sight, without real sites

`scripts/standin.py` serves pages that answer like Cloudflare's check (`403`, `cf-mitigated: challenge`), so the desktop app passes them in Edge, and stands in for real sites by the `Host` it is asked for (next section):

```sh
ss -ltnp | grep -q ':8799 ' && echo "8799 is taken: another session's stand-in? Use another port and folder"
python3 -I .agents/skills/haul-windows-test/scripts/standin.py "$SCRATCH/standin" 8799 2> "$SCRATCH/standin.log" &
```

Another session may run its own stand-in at the same time: never reuse its port, folder or log.

| Page                             | What it does                                                         | Expect (`pass` `end` `outcome`)                             |
| -------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- |
| `/guard/empty`                   | passes and lists nothing                                             | `settled`, then the row under Needs you (a paste fails)     |
| `/guard/swap`                    | its two links become two files on `localhost` after 4 s (same count) | `listed`, and `Ex.part1.rar`, `Ex.part2.rar` paused         |
| `/guard/filepage-a/Ex.part3.rar` | a file's page (its path names it) that also links two other files    | not `listed`: the row stays `Ex.part3.rar`, under Needs you |
| `/guard/stuck`                   | a Turnstile field that never fills                                   | `wants_person` after the pass's time                        |
| `/guard/adpage-a/Ex.part4.rar`   | a file's page whose ad sends the window to `localhost` after 1 s     | `page` `sent back`, then `refused` with the row's `id`      |

A page passed in Haul's own window rather than Edge (as on a machine without Edge) is what Open here shows: start the test copy with `HAUL_CHROMIUM` set to a path that does not exist, and its `page` signals tell what the window did. Such a window comes on screen once the pass's time is up; stop the test copy before then to keep it off the user's screen.

Windows reaches the server at `127.0.0.1:8799` and `localhost:8799`, which Haul counts as two sites. Add `-<anything>` to a `/guard` page's path for a fresh address. Stop the server by its port (`ss -ltnp | grep ':8799 '` gives its pid) and `kill`, and delete its folder.

## Real sites, stood in for

Stand-in mode (`docs/debugging.md`, "Real sites, stood in for") makes `<site>.localhost:<port>` stand for `<site>` in a test copy: Haul recognises it as that site, and every real address it asks for, from its own client, the page windows or Edge, goes to `http://<site>.localhost:<port>` instead. So wrappers, pastes and hosts are tested end to end with no real site and none of the user's access. Start the test copy with the server's port as `HAUL_STAND_IN`, next to `HAUL_DEBUG=1` (Haul 0.12.0 and later; it has no effect without debug mode asked for at the start):

```sh
powershell.exe -NoProfile -Command "\$env:HAUL_DATA_DIR='$W\\data'; \$env:HAUL_PORT='8791'; \$env:HAUL_DEBUG='1'; \$env:HAUL_STAND_IN='8799'; Start-Process -FilePath '$W\\Haul.exe'"
dbg -d '{"text":"https://releases.example/example-set"}' "$B/api/add"
```

Add links in their real form (`https://filecrypt.cc/Container/GGGGGGGG.html`) or by their stand-in address (`http://filecrypt.cc.localhost:8799/Container/GGGGGGGG.html`); both reach the stand-in. Everything is made up. A stand-in page whose last path part ends in `-check` (or `-check2`) is behind one (or two) rounds of the stand-in check: a `403` "Just a moment..." page with `cf-mitigated: challenge` that sets a `cf_clearance` cookie and loads itself again after 1.5 s. filecrypt containers always are. The server encrypts Click'n'Load data with the `openssl` command.
